GraphRAG Engine

IN PROGRESS

A GraphRAG system on Neo4j, benchmarked against a strong hybrid retrieval baseline on 2WikiMultiHopQA. The goal is a fair answer to one question: when does a knowledge graph actually help multi-hop question answering, and when does it not? It showed that hybrid retrieval never finds the bridge entities that multi-hop questions need, which is what the graph is built to fix.

+20 pts EM, retrieval vs model memory (95% CI 9 to 31) · 12,547 relations from 2,049 documents · extraction recall 0.75, slot precision 0.89 (strict, full run, 247 dev triples)

  2. LLM entity and relation extraction with strict JSON schema output: 12,547 relations for 0.35 USD
  3. Entity resolution keeps same-name entities apart and records why every merge happened
  4. Hybrid baseline: BM25 + E5 dense + bge reranker, the retriever from the MSc thesis
  5. Short answers from gpt-oss-120b, pinned provider, every LLM call cached and logged with cost
  6. EM and F1 with 95% bootstrap confidence intervals, quality bars fixed before results

MSC THESIS FINDING

The fusion weight

Sparse and dense retrieval are not equal partners. Assuming they are costs you accuracy.

Most hybrid RAG implementations split BM25 and dense embedding retrieval 50/50 by default. I ran eleven systematic experiments and found the best tested value at alpha=0.70, confirmed with a paired t-test (p=0.002). That calibration choice is worth +2.9 pts over alpha 0.5 (p = 0.002, 95% CI +1.1 to +4.7), +11.4 pts over BM25 only, on 8.84M passages.

The common assumption of alpha=0.50 was tested directly and found to be suboptimal.

ENGINEERING DIARY

Decisions and failures, with receipts

Real entries from the repos, newest first. Each one links to the commit or document it comes from.

  1. 2026-10-08GraphRAG EngineFIX

    Judge prompt v2, a cannot-link rule and a pilot in both directions

    Each side of a candidate pair now states its role ("the subject of its paragraph" or "mentioned in a paragraph about X"), and the judge decides on the named entity only. Union-find refuses a merge when any pair across the two clusters was judged "different", and merges run in a fixed order. The new pilot tests both directions: at least 22 of 24 known bridge links must be judged "same", and the bad merges from run 1 must be judged "different". It passed both gates. The full re-run is in progress.

    Commit 71d639d →docs/NEXT.md, section 3 →
  2. 2026-10-08GraphRAG EngineFAILURE

    Entity resolution run 1 failed, and it stays on record

    Run 1 judged all 17,309 candidate pairs for 0.59 USD. It merged the United States with the United Kingdom (117 mentions), and bridge link recall on the report split fell from 0.83 to 0.51. Two causes: the judge prompt confused a mention with the subject of its paragraph, and there was no cannot-link check, so 2,439 pairs judged "different" still ended up in one cluster. All outputs are kept in results/m3/run1_flawed.

    Commit 60e5c25 →Commit 8e7cdf7 →docs/NEXT.md, section 2 →
  3. 2026-10-08GraphRAG EngineDECISION

    Plan and quality bar written down before any code

    Before writing entity-resolution code, the plan and its quality bar went into docs/PLAN.md: at least 48 of 50 seeded-random merges correct on the report split. After the first pilot, auto-merge was turned off: dev gold triples give no same-name negatives, so the merge threshold cannot be tuned from gold.

    Commit 76f4fb8 →docs/PLAN.md, M3 →
  4. 2026-10-04GraphRAG EngineDECISION

    Prompt v3 failed one bar, and a rule fixed in advance decided

    The extraction quality bar (recall of at least 0.75, slot precision of at least 0.90, at least 27 of 30 hand-checked triples correct) and the rule for a failed prompt v3 were both committed before the run. On the pilot's 9 fresh batches (21 dev triples), prompt v3 passed recall (0.76) and failed slot precision (0.76). All 10 failures were classified by hand: 1 real miss, 0 wrong facts. The hand check found 28 of 30 triples correct. Under the rule, the full corpus was extracted with prompt v3 and the strict score is reported as it is.

    Commit f780be6 (bar) →Commit e108983 (rule) →Commit a41717a (pilot) →Commit 9d891d0 (full run) →docs/PLAN.md, M2 →
  5. 2026-10-01shipment-intake-aiDECISION

    Re-queue a failed email without rewriting its history

    After a quota or API outage, POST /review/{id}/retry re-queues a failed email. The attempts counter is not reset, because it is the lock token and the attempt number in the history; retry_base records where the new budget starts. After a requeue with MAX_ATTEMPTS=8, the log shows attempt=9/16.

    Commit 12cf11c →README, review and feedback loop →
  6. 2026-10-01shipment-intake-aiDECISION

    Dangerous goods are never auto-accepted

    Two independent checks send dangerous goods to review: the model's cargo class, and a plain-code marker check (ADR, Gefahrgut, UN numbers, hazmat, IMDG). Negated mentions such as "kein Gefahrgut" do not trigger it, and ADR is matched in capitals only, so "Adr." (Adresse) does not either. The check errs toward review: a false positive costs one review, a false negative auto-accepts dangerous goods.

    Commit 1c97b8c →README, dangerous goods →
  7. 2026-10-01shipment-intake-aiDECISION

    The model extracts, the rules decide

    The model only fills in fields and a confidence per field; the output schema has no decision field. Deterministic code accepts an email or sends it to review with stable reason codes such as missing:weight. The model's self-reported confidence is not well calibrated, so it is one check among several.

    Commit 22c111a →README, design decisions →
HOW I ENGINEER AI SYSTEMS

From problem to production

I build, evaluate and deploy practical ML systems, from data preparation and experimentation to APIs, cloud deployment and monitoring.

01 · UNDERSTAND

Define the problem

Translate the product or business problem into a concrete ML problem with measurable success criteria.

02 · EVALUATE

Choose metrics first

Define Recall@10 and RAGAS Faithfulness before optimising. Metrics chosen for the problem, not retrofitted.

03 · BASELINE

Establish a baseline

Understand whether the new approach improves anything. alpha=0.70 gave +2.9 pts over the default alpha 0.5 (p = 0.002).

04 · DATA

Prepare and validate

Check data quality, distribution, edge cases, and leakage before training. Real-world document formats handled properly.

05 · EXPERIMENT

Track systematically

Every experiment recorded with its settings and results; 11 alpha experiments, results in RESULTS.md, validated with a paired t-test.

06 · TRADE-OFFS

Analyze trade-offs

Accuracy vs latency. The extra cost of running two retrievers must be justified by the Recall@10 gain.

07 · DEPLOY

Package reproducibly

Docker, Kubernetes, systemd. Services that restart on crash, roll out with zero downtime, behave identically in dev and prod.

08 · TEST AND MONITOR

Test and monitor

12 pytest regression tests. Prometheus /metrics and /health. GitHub Actions CI/CD that fails the build on regression.

09 · ITERATE

Improve from evidence

Use observed failures and evaluation results to drive the next experiment. Evidence from production, not intuition.
